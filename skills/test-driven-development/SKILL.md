# Test-Driven Development & Verification Master (TDD-VM)
## TDD × 完了前検証ゲート × テスト戦略 × カバレッジ 統合最高峰マスター

> **⚔️ 【鉄の掟】The Iron Law of Verification**:
> `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`
> （新鮮な実機検証コマンドの実行証拠（Exit Code: 0 / 0 Failures）がない限り、いかなる完了・成功・修正完了の主張も永久に禁止する）

本スキルは、開発者が陥りがちな「動くはずという推測での完了報告」を100%遮断し、**テスト先行（TDD）、網羅的カバレッジ、そして完了前の客観的検証を絶対的に保証する** ソフトウェア品質保証の旗艦フレームワークです。

## 🚪 第1部：完了前検証ゲート（The Verification Gate Function）

コードの修正、機能追加、バグ修正、タスク完了を宣言する直前に、**必ず以下の5ステップゲートを通過**しなければならない。

```
       ┌────────────────────────────────────────────────────────┐
       │ 1. 🔍 IDENTIFY: この完了を客観的に証明するコマンドは何か？ │
       │    (pytest, python3 test.py, curl API疎通, linter等)   │
       └──────────────────────────┬─────────────────────────────┘
                                  │
       ┌──────────────────────────┴─────────────────────────────┐
       │ 2. ⚡ RUN: その検証コマンドを「今すぐ」「完全に」実行する│
       │    (過去の実行結果やキャッシュに頼らず、最新状態で実行) │
       └──────────────────────────┬─────────────────────────────┘
                                  │
       ┌──────────────────────────┴─────────────────────────────┐
       │ 3. 📖 READ: 出力ログ、終了コード(Exit Code)、失敗数を確認│
       │    (1つのエラー、警告、未補足例外も見逃さず直視)       │
       └──────────────────────────┬─────────────────────────────┘
                                  │
       ┌──────────────────────────┴─────────────────────────────┐
       │ 4. 🛡️ VERIFY: 出力結果は完了の主張を 100% 裏付けているか？│
       │    ├─ NO  ➔ 失敗箇所を特定し、実装を修復（再テストへ） │
       │    └─ YES ➔ 客観的証拠ログを添えて初めて完了主張可能  │
       └──────────────────────────┬─────────────────────────────┘
                                  │
       ┌──────────────────────────┴─────────────────────────────┐
       │ 5. 🏆 CLAIM: 証拠（ログ・テスト結果）と共に拓磨様へ報告 │
       └────────────────────────────────────────────────────────┘
```

### 🚫 禁止される「赤信号（Red Flags）」ワード
以下の表現や思考が出た瞬間、直ちに作業を停止し検証コマンドを実行すること：
- ❌ 「〜のはずです」「おそらく動きます」「問題ないと思われます」
- ❌ 検証コマンドを実行する前に「できました！」「完璧です！」と述べること
- ❌ 「今回だけはテストを省略して……」という妥協
- ❌ エラーが出た際に、テスト側の期待値を勝手に緩めて合格に見せかける行為（最大の背信）

## 🔄 第2部：厳格な Red-Green-Refactor サイクル

実装コードを1行も書く前に、まずテストコードを作成する。

```
   🔴 RED (失敗の確認)        🟢 GREEN (最小実装で合格)      🔵 REFACTOR (美しく洗練)
 ┌──────────────────────┐    ┌──────────────────────┐    ┌──────────────────────┐
 │ 期待される振る舞いを │ ➔ │ テストをPASSさせる   │ ➔ │ 重複を排除し、コード │
 │ 表すテストを作成し、 │    │ 最もシンプル・最小限 │    │ の可読性・構造を洗練 │
 │ 意図通り「失敗」確認 │    │ の実装コードを記述   │    │ （テストは緑を維持） │
 └──────────────────────┘    └──────────────────────┘    └──────────────────────┘
            ▲                                                           │
            └───────────────────────────────────────────────────────────┘
```

### 1. 3原則
1. **テスト先行の原則**: 失敗するテストが存在しない限り、いかなる本番コードも書いてはならない。
2. **最小限の原則**: テストを通過させるために必要最小限のコードのみを実装する（過剰設計の排除）。
3. **継続的検証の原則**: リファクタリング時は1ステップごとにテストを回し、常にGreenを維持する。

## 🏛️ 第3部：3層テストピラミッド＆テスト戦略設計

単一のテスト手法に偏らず、以下のバランスでテストスイートを構成する。

```
             /             / E2E \       10% : Playwright / WebApp 統合実機検証
           /───────          /  Integ  \     20% : API疎通, DB連携, モジュール間結合
         /───────────        /    Unit     \   70% : 関数, ロジック, 境界値, エッジケース
       /───────────────```

### 1. 単体テスト（Unit Tests: 70%）
- 純粋関数のロジック、データ変換、アルゴリズムをミリ秒単位で高速検証。
- **エッジケース網羅マトリクス**:
  - 境界値（0, -1, 最大値, `sys.maxsize`）
  - 特殊入力（`None`, 空文字 `""`, 空リスト `[]`, 巨大文字列, 制御文字）
  - 型不整合・例外送出（無効な引数に対する適切な `ValueError` / `TypeError`）

### 2. 結合テスト（Integration Tests: 20%）
- データベース（SQLite/WAL）、ファイルI/O、外部APIクライアント、MCPサーバーとの通信疎通。
- モックを使用する場合は、インターフェースの型シグネチャと完全一致させる。

### 3. E2E / システムテスト（10%）
- ユーザーシナリオに基づく一気通貫の動作確認（`webapp-testing` と連携）。

## 🛠️ 第4部：失敗テストの体系的修復プロトコル（Fix-Tests Guide）

テストが失敗（FAIL / ERROR）した際の対処手順：

1. **エラーメッセージとトレースバックの完全精読**:
   - 表面的な行番号だけでなく、スタックトレースの最深部から原因となった引数・状態を特定。
2. **テストコード vs 実装コードの判定**:
   - 仕様が変更されていない限り、**「テストコードが正しい」** と仮定し、**「実装コードのバグを修正」** する。
   - テストを勝手にコメントアウトしたり、アサーションを削除することは重大な規約違反。
3. **再帰的検証**:
   - 1箇所を直したら、影響を受ける関連テストスイート全体を再実行し、デグレード（先祖返り）がないことを確認。
